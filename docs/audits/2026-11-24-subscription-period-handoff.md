# 订阅跨期接续排查（2026-11-24）

## 范围与结论

基线 main / f979f47。以下前半部分为修复前的排查记录。用户随后授权修复、推送及部署；最终实现与验证见文末。本批不修改真实商家订阅或主动删除真实折扣。

已确认：本地 validUntil 到期的访问校验不直接安排或执行折扣删除。全量订阅核验能选中已开始的下一期，保存新的有效期并取消待处理失效任务。不过，当前实现不能保证无缝接续：本地旧权益快照会短暂拒绝访问；携带旧 sub_id 的即时通知核验可能漏查下一期并安排失效任务。

## 提示修改

存在有效下一期且不属于7天内空档警告时，简体中文分两行显示：

```text
当前套餐将于2026/12/23 17:00到期，
下一期套餐将于2026/12/23 17:00生效。
```

日期仍按店铺时区格式化，示例按 Asia/Shanghai。同步16种应用语言。无下一期仍显示到期失效说明；下一期与本期有空档且本期7天内到期时，保留既有红色警告及失效说明，同时下一行显示下一期生效时间。续费继续复用现有原生套餐跳转。未修改CSS。

## 实际代码路径

1. `worker/src/routes/subscription-access.ts` 的 hasSubscriptionAccess 仅检查 state、功能权限、validUntil/graceUntil，忽略已核验的 nextValidFrom/nextValidUntil。本期到期后、后台同步前，bootstrap可返回无访问权/套餐页，受保护写接口403，公开组件配置查询404。此函数不入队失效任务。
2. `worker/src/services/entitlements.ts` 全量核验在下一期 startAt <= now 后，将其作为当前候选；详情具有 quantity_breaks_access 时 writeActive，并取消失效任务。列表本身不足以授权，详情功能权限也必须确认。
3. `worker/src/index.ts` appsubscription/expiration 即时处理把旧 sub_id 传给 processSubscriptionOperations。EntitlementService 第1页按该 ID 过滤，若平台返回 lastPage=true，就不会查到下一期。
4. 仅查旧记录时：expired 可进入24小时宽限并清空下一期字段；unactive/cancelled/pending 可写 unknown、清空权限并 enqueueExpiryOperations。该风险以平台实际返回旧记录状态为条件，不表示每条 expiration 通知都必然误停。
5. `worker/src/jobs/subscription-operations.ts` pause_campaign 执行前读权益，trial/active/grace会跳过，否则调用删除接口并把活动按订阅失效处理。没有任务权益版本核对，也没有删除前重新全量核验当前有效订阅。核验恢复有效后会取消失效任务，但取消不能保证拦截已经越过权限检查、正在调用平台的删除请求。该并发风险由代码检查发现，本次未模拟实际外部删除竞态。
6. 每5分钟Cron处理已有队列；每日03:00 UTC全量核验active/grace/review_pending及待处理任务商家。没有在每个 validUntil 时刻自动晋升下一期的逻辑。页面查询会异步触发核验，但响应先使用本地快照。

## 排查时提出的后端修复方案

1. 到期通知不得只凭旧订阅判定店铺无权益；全量分页查询店铺订阅、验证当前有效套餐详情后再决定是否失效。
2. 已核验、时间连续的下一期在交接时提供有限且明确的本地访问接续；不能仅因存在任意未来订阅就允许跨越空档，也不能仅凭通知体授予权限。接续时仍后台全量核验，平台明确撤销后停止接续。
3. 失效任务在执行破坏操作前重新核验、检查任务权益版本及活动绑定，并为已开始的删除请求设计防竞态机制。只取消队列记录或只在删除前读一次状态，都不能提供原子保证。
4. 针对精确交接时刻、旧ID通知、延迟/重复通知、平台失败、下一期被取消、订阅空档、失效/恢复并发补充回归，再实施上线。

## 授权后的最终修复

- EntitlementService不再按通知sub_id过滤权益查询，始终分页查询店铺全部订阅，当前候选同时校验startAt/endAt；结束但status仍为active的记录走既有过期宽限规则。
- 共享domain/entitlement-access判定支持已核验、时间连续且已开始未结束的下一期。仅对有效active/trial及quantity_breaks_access授权；不跨空档。下期被明确取消后的全量核验会清空下期；支付通知遇Partner失败保留原先已核验的下期时间。
- 权益核验和折扣失效使用独立键subscription:appKey:handle，复用D1锁表、20分钟租约，无新迁移；同店串行，不同店独立。锁内仓库写权益时SQL核对持有者/租期，阻止旧持有者迟到覆盖新权益。异常释放，崩溃后需等待租期到期，期间保留已核验本地访问、后台后续重试。
- 失效任务先检查任务仍运行、当前权益版本和访问权，再重新全量核验；Partner失败时抛给队列重试，不调用删除。核验恢复访问时取消失效任务。
- 真正删除同时持有活动发布锁；在实际DELETE前及确认返回后检查订阅租约、活动锁、任务状态/版本和折扣绑定，防止把变更后的活动标记为失效。仍使用现有Function删除接口与shoplineAdminHeaders。远端删除响应不确定无法提供跨系统原子回滚，继续依赖原有核验与重试，未宣称平台层绝对无竞态。
- 独立审查发现：失效前核验升级权益版本可能漏掉其他活动/重试，或新建立即到期任务绕过Retry-After。已修复：该核验不新建重复失效任务，在锁内同步原队列任务的权益版本，保留各自key、状态、次数和next_attempt_at；同批后续任务重新读取当前版本。
- 商家GDPR清理一并删除对应订阅锁，保留其他商家锁；有真实D1隔离回归。
