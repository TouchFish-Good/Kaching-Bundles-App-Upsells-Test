# SHOPLINE 单套餐订阅与授权设计

## 目标

为“多件折扣”接入一个 SHOPLINE 应用套餐：首次 7 天试用，之后按月收费 USD 9.99；月付的一个账期固定按 30 天计算。宽恕期固定为 1 天。每个 SHOPLINE 店铺只能试用一次；套餐确认失效后，暂停全部已启用活动并停止主题扩展渲染。自动续费、宽恕期和 Webhook 时序问题均不得误暂停活动。

SHOPLINE 是计费权威。应用不自行扣款、不以本地时钟计算续费，也不只依赖浏览器回跳开放权限。应用持久化一份订阅权益镜像，用于权限判断、暂停任务、重试与审计。

## 已确认的平台能力

以下事实来自用户提供的《应用订阅配置说明.docx》。实现前仍必须以其中链接的 SHOPLINE 官方 Webhook 文档确认实际 topic、载荷、签名校验、重试机制和确认响应；本文不臆造这些细节。

| 范围 | 已确认行为 |
| --- | --- |
| 商品模型 | `应用套餐` 是周期订阅，套餐之间互斥。 |
| 收费周期 | 平台套餐可按月或按年收费；月付的一个账期按固定 30 天计算。 |
| 试用 | 订阅组可设置 0 至 30 天试用，本设计使用 7 天。 |
| 自动续费与宽恕期 | 应用套餐支持自动续费；本应用已配置 1 天宽恕期。套餐到期或续费失败后，商家在此 1 天内仍可继续使用服务以完成续费。 |
| 失效通知 | 自动续费成功进入下一期时，平台不发送套餐失效通知。 |
| 订阅状态 | `pending`、`active`、`expired`、`unactive`、`cancelled`。 |
| 订阅类型 | `trial`、`paid`、`preorder`。 |
| 权益 | 订阅详情接口提供 `feature_key_list`。 |
| 取消与退款 | 目前由平台后台人工处理，应用不得承诺自助取消或退款。 |

## 应用市场配置

只创建一个付费应用套餐及一个订阅组：

| 配置项 | 值 |
| --- | --- |
| 商品模型 | 应用套餐 |
| 套餐 key | `ultra` |
| 应用名称 | 多件折扣 |
| 套餐名称 | Ultra |
| 价格 | USD 9.99 |
| 收费周期 | 月付（每个账期固定 30 天） |
| 试用期 | 订阅组设置为 7 天 |
| 功能点 key | `quantity_breaks_access` |
| 订阅组 | 一个订阅组，仅包含此套餐 |
| 套餐等级 | 最低且唯一的等级 |

前台文案统一使用“USD 9.99 / 月（每 30 天）”，明确月付按固定 30 天计费。SHOPLINE 也支持年付，但当前仅创建此月付 `Ultra` SKU；新增年付 SKU 前必须先补充价格、SKU 校验、套餐切换和权益测试。本期不创建免费套餐、增值服务、年付 SKU 或一次性商品。

“多件折扣”是应用名称，`Ultra` 是套餐名称。应用市场的功能描述使用“为商品配置多件阶梯优惠”这类可验证的功能表述，不使用“最低价”“最优惠”“保证提升销量”“100%”等绝对化、比较性或效果承诺文案。商品页展示的原价、优惠价和节省金额必须来自商家配置与实际结算规则。

## 核心业务规则

### 计费与授权边界

SHOPLINE 是计费状态的唯一权威；应用权益服务是“多件折扣”后台路由、服务端 API、活动发布和主题扩展数据的授权权威。只有订阅查询确认存在有效应用套餐，且详情接口确认 `feature_key_list` 包含 `quantity_breaks_access` 时，应用才开放权限。

浏览器回跳、前端本地状态、收银台看似完成的页面和 `auto_recurring=true` 都不能单独授予权限。

### 每店仅一次试用

试用资格主体固定为：

```text
app_key + SHOPLINE handle
```

不得使用浏览器、Cookie、员工账号、邮箱、本地存储、套餐 SKU 或订阅 ID 作为试用主体。这样可阻止同一店铺借助重装应用、更换设备或浏览器、反复打开结算、以后新增套餐等方式获得第二次试用。

仅当订阅查询确认店铺已真实进入试用订阅时，应用才写入“已消耗试用”。创建支付链接或点击“开始试用”不会消耗资格，避免商家中途离开后无法再开始首次试用。

不同 `handle` 的 SHOPLINE 店铺是不同主体。没有平台可验证的商家主体 ID 时，应用不能承诺阻止同一人创建多个独立店铺并分别试用。

### 续费后不自动恢复活动

套餐失效时，活动以原因 `subscription_expired` 暂停。续费成功只恢复应用访问权限，不能自动发布旧活动；商家必须检查商品、价格、排期和冲突后手动恢复。这样可避免长期断订后重新开启过期促销。

### 店铺隔离

每一个订阅、权益、活动、发布记录、缓存项、后台任务、锁和前台请求都必须带有当前认证店铺的 `handle`。禁止存在任何“应用已过期”或“当前套餐状态”的全局布尔值，也禁止从上一个请求、浏览器缓存或后台任务复用其他店铺的 `handle`。

店铺 A 的失效 Webhook 只能读取和写入 `handle=A` 的权益、活动和操作任务；它绝不能扫描、暂停或覆盖店铺 B 的任何记录。后台任务的操作键和发布锁都包含 `handle`，例如 `subscription-expired:<handle>:<version>`；权益缓存键也必须至少包含 `app_key`、`handle` 和 `version`。

管理后台路由从认证会话取得 `handle`，公开前台接口仅用经过格式校验的 `shop` 查询参数查找同一 `handle` 的权益。Webhook 使用经签名验证的载荷中店铺标识。三种入口均不得接受客户端声称的“当前订阅状态”。

## 数据模型

存储实现应遵循当前仓库迁移方案，但必须有以下记录和约束。

### 店铺权益

| 字段 | 说明 |
| --- | --- |
| `app_key`、`handle` | 共同组成唯一键。 |
| `state` | `unknown`、`trial`、`active`、`grace`、`review_pending`、`inactive`。 |
| `feature_keys` | 最近确认的权益列表；必须有 `quantity_breaks_access`。 |
| `active_subscription_id`、`active_spu_key` | 当前有效订阅与套餐的审计信息。 |
| `valid_from`、`valid_until` | 平台返回的订阅起止时间。`valid_until` 仅可作为平台已确认到期后的 1 天宽恕期起点，不能在到期瞬间直接停用。 |
| `grace_until` | 根据已确认的 `valid_until` 和固定 1 天宽恕期计算；仅用于宽恕期展示与最终失效前的复查门槛。 |
| `auto_recurring` | 提示字段，不可单独作为授权依据。 |
| `last_verified_at` | 最近成功同步时间。 |
| `version` | 单调递增版本，用于缓存失效、竞态和事件乱序保护。 |

### 试用账本

| 字段 | 说明 |
| --- | --- |
| `app_key`、`handle` | 共同组成唯一键。 |
| `trial_consumed_at` | 首次确认试用权益的时间。 |
| `trial_subscription_id` | 消耗资格的 SHOPLINE 订阅 ID。 |
| `source_event_id` | 对应的 Webhook 或同步事件，供审计使用。 |

此记录在正常业务中只追加、不重置。卸载、订阅失效或重新配置套餐均不能删除它。

### 订阅订单与操作队列

每次支付创建都记录唯一 `out_trade_no`、`handle`、`spu_key=ultra`、月付 30 天 `sku_id`、支付状态、时间戳以及已知的 `sub_id`。Partner API Token 永不写入订单表或浏览器。

同步和暂停使用可持久化、可重试的幂等操作：

| 字段 | 说明 |
| --- | --- |
| `operation_key` | 例如 `subscription-expired:<handle>:<entitlement-version>`，必须唯一。 |
| `kind` | `reconcile`、`pause_campaign`、`disable_storefront`、`resume_check`。 |
| `state` | `pending`、`running`、`succeeded`、`retrying`、`blocked`、`failed`。 |
| `attempts`、`next_attempt_at`、`last_error` | 重试控制，不记录机密。 |
| `campaign_id` | 单个活动暂停任务的目标。 |

## SHOPLINE 接口契约

所有 Partner API 调用由服务端执行，使用受保护的 `X-Shopline-Access-Token`。`app_key` 和 `handle` 来自认证会话/租户上下文，不能相信浏览器任意参数。

| 用途 | 方法和路径 | 处理要求 |
| --- | --- | --- |
| 查询套餐 | `GET /v20220901/app_subscribe/productList.json` | 在服务端读取产品与 SKU，供诊断或受控结算创建使用。 |
| 创建结算 | `POST /v20220901/app_subscribe/create_pay.json` | 创建唯一 `out_trade_no`；传入 `app_key`、`handle`、`spu_key=ultra`、月付 30 天对应的 `sku_id`、回跳地址和 `USD`；跳转返回的 `url`。 |
| 查询支付 | `GET /v20220901/app_subscribe/charges/status.json` | 仅 `200=已支付` 表明订单支付成功；之后仍必须同步订阅才可开放权限。 |
| 查询订阅 | `GET /v20220901/app_subscribe/list.json` | 查询 type-1 应用套餐，不能只看最近订单。 |
| 查询权益 | `GET /v20220901/app_subscribe/detail.json` | 读取有效订阅的 `feature_key_list` 并要求包含 `quantity_breaks_access`。 |
| 计量权益 | `PATCH /v20220901/app_subscribe/rights_minus.json`、`rights_plus.json` | 本套餐无限额，不调用。 |

`create_pay` 支持传入 `sub_id` 升级套餐，但单套餐设计不使用该字段。以后增加套餐时，试用仍须受应用级试用账本限制。

## Webhook 处理

订阅文档中列出三类事件：

| 事件 | 作用 | 处理规则 |
| --- | --- | --- |
| 套餐订阅通知 | 商家订阅或升级套餐。 | 放入同步队列，不能直接按 Webhook 载荷授权。 |
| 套餐失效通知 | 已订阅套餐失效；自动续费成功时不发送。 | 写入 `review_pending`，复查订阅后才允许暂停。 |
| 支付结果通知 | 商家完成支付，成功或失败都会触发。 | 更新对应 `out_trade_no`；成功后同步订阅。 |

按官方说明校验每个 Webhook 的签名，事件被可靠持久化或入队后才返回成功。应优先使用平台事件 ID 作为幂等键；若没有该字段，从已签名载荷内的稳定标识与事件类型构造幂等键。重复、重试、延迟和乱序都不得造成二次试用、重复暂停或旧失效状态覆盖新有效状态。

## 权益同步和自动续费保护

### 有效权益判定

1. 查询店铺所有 type-1 应用套餐。
2. 查找状态为 `active` 的当前试用或付费订阅。
3. 调用详情接口确认该订阅含 `quantity_breaks_access`。
4. 有效试用写入 `trial`；有效付费订阅写入 `active`。
5. `preorder` 自身不能证明当前可用；可能与当前付费期并存，不能覆盖当前权益。
6. 当平台确认当前订阅到期或续费失败，但已验证的 `valid_until` 起算尚未超过 1 天宽恕期时，写入 `grace`，继续授予全部应用权限，并显示准确的宽恕期结束时间。
7. `pending`、`expired`、`unactive`、`cancelled` 在宽恕期外不授予权益。

平台状态是授权权威。`end_at` 不能在到期瞬间直接停用活动；它只在平台已确认到期/续费失败后用于计算已配置的 1 天宽恕期终点。宽恕期结束前不能暂停活动；宽恕期结束后仍须重新查询平台订阅才可失效。

### 自动续费不误暂停

```text
收到失效事件或执行定时同步
  -> 写入 review_pending
  -> 查询所有 type-1 应用套餐
  -> 是否存在含所需功能点的 active 订阅？
       是：写入 trial/active，取消待执行暂停任务
       否：是否仍处在已配置的 1 天宽恕期？
              是：写入 grace，保留全部权限，到 grace_until 前后再次同步
              否：短暂延迟后再次同步
                    -> 仍无有效权益：写入 inactive，创建暂停任务
```

第二次同步用于处理支付、Webhook 与订阅查询的短暂传播延迟。宽恕期则是明确的产品规则：从平台确认的订阅到期/续费失败开始，固定持续 1 天；在此期间状态为 `grace`，所有页面、API 和主题扩展均继续可用。自动续费成功时平台会保留或切换到有效权益，且资料说明此时不会发送失效通知；即使意外收到旧失效事件，复查仍会阻止暂停。

### 同步触发点

- 每个订阅 Webhook；
- 支付回跳后的支付成功确认；
- 已认证商家进入应用；
- 打开“套餐与账单”页；
- 每日后台对账；
- 对最近有效店铺执行破坏性暂停前。

Partner API 暂不可用时，保留最近确认的状态并重试，不能仅因查询失败把有效店铺置为失效。

## 页面与 API 访问策略

### 页面路由守卫

权益为 `trial`、`active` 或 `grace` 时，正常使用“多件折扣”的活动、组件样式和翻译页面。权益为 `unknown`、`review_pending` 或 `inactive` 时，所有受保护页面统一进入应用内套餐页：

```text
/quantity-breaks
/quantity-breaks/new
/quantity-breaks/:campaignId
/quantity-breaks/widget
/quantity-breaks/translations
  -> /quantity-breaks/plan
```

以下路径必须例外，防止循环或阻断恢复：

- `/quantity-breaks/plan`；
- 支付回跳/订阅确认路径；
- 认证、卸载、隐私清除、Webhook、健康检查和静态资源；
- 如新增，范围明确的支持联系路径。

页面守卫只跳转应用内付费页，不能自动送往外部 SHOPLINE 收银台。商家主动点击“开始 7 天试用”“立即订阅”或“立即续费”后才跳转支付，避免反复外跳并能清楚显示失败与重试。

### 服务端接口守卫

每个状态变更接口都独立验证权益：活动创建、保存、发布、暂停/启用、样式保存、翻译保存及相关写操作。失效店铺返回结构化 `403`，错误码为 `SUBSCRIPTION_REQUIRED`，绝不返回 HTML 重定向。浏览器收到该错误后跳转套餐页；前端守卫仅改善体验，服务端是安全边界。

## 套餐与账单页面

因为只有一个套餐，不设计套餐比较卡。

### 无权益状态

保留现有“多件折扣”应用壳，用精简付费页替代受保护内容：

```text
开始 7 天免费试用
免费使用全部多件折扣功能 7 天。
之后 USD 9.99 / 月（每 30 天）。

[ 开始 7 天试用 ]
```

已消耗试用且无有效权益时显示：

```text
继续使用多件折扣
USD 9.99 / 月（每 30 天）。

[ 立即订阅 ]
```

未经额外验证，不写“随时取消”，不承诺应用内退款或取消。

### 试用、有效和失效状态

使用紧凑状态条，不反复弹窗：

| 状态 | 文案 | 操作 |
| --- | --- | --- |
| 试用中 | `免费试用还剩 N 天` | 查看套餐 |
| 试用最后两天 | `试用将在 N 天后结束` | 立即订阅 |
| 已付费 | `Ultra · USD 9.99 / 月（每 30 天）` 和平台续费日期 | 管理套餐 |
| 宽恕期 | `续费宽限期还剩 N 小时` | 立即续费 |
| 待复查 | `正在核验订阅状态` | 再次检查 |
| 已失效 | `需要订阅才能继续使用活动` | 立即续费 |

“管理套餐”只能在确认 SHOPLINE 管理入口后才展示。过期页明确说明活动已暂停、前台组件已隐藏；续费成功后列出 `subscription_expired` 暂停的活动供商家逐项恢复。

## 确认失效后的暂停流程

当两次权威同步都确认没有有效权益时，执行以下持久化流程。首先切断前台数据，保证平台清理失败时消费者也不会继续看到优惠。

```text
1. 写入 entitlement = inactive，并递增权益版本。
2. 前台活动接口不再返回该 handle 的活动。
3. 枚举该店铺全部 Active 活动。
4. 为每个活动创建一个幂等暂停操作。
5. 复用现有安全暂停流程，停用/删除平台自动优惠。
6. 平台确认后，将活动写为 Paused，原因 subscription_expired，
   并记录对应权益版本。
7. 未完成任务按持久化退避策略重试，并提供运维诊断。
```

现有暂停流程会先删除已发布的平台自动优惠，再完成本地暂停。订阅失效必须复用该流程，不能仅改本地状态。后台任务需要取得有效的 SHOPLINE Admin 会话/Token；若暂时不能取得，权益与前台闸门仍立即失效，平台暂停任务保持重试，并在无法恢复时要求重新授权。

分类活动还必须复用现有的分类变量清理逻辑。暂停操作需获得店铺发布锁，避免与商家同时发布活动发生竞态。

## 主题扩展行为

主题前台必须 fail closed：

1. `storefront-campaign` 在读取活动前检查店铺权益。
2. 只有确认的 `trial`、`active` 或 `grace` 店铺可取得活动数据；其他状态都不返回活动。
3. 主题扩展遇到无活动、`403`、`404` 或订阅必需响应时，进入终止性“不渲染”状态。
4. 若当前页面已创建组件容器，脚本须清除容器内容，不能残留旧价格、优惠或加购 UI。
5. 权益相关前台响应保持不可缓存，CDN 或浏览器不得在失效后提供旧活动。

这不是 CSS 隐藏。公开活动接口不应向失效店铺返回活动配置；没有当前有效数据时，主题扩展必须完全不渲染。

## 平台折扣被手工删除时的发布对账

商家可能直接在 SHOPLINE 折扣列表中删除由本应用创建的自动折扣。此时本地 `campaign.status=active` 和已保存的 `platformDiscountId` 不能继续被视为真实发布状态，否则应用会显示“已启用”，主题组件也可能继续展示一个在结账中不会生效的优惠。

必须新增发布对账流程：

1. 对每个本地为 `active` 或 `scheduled` 且拥有 `platformDiscountId` 的活动，使用经官方文档确认的 SHOPLINE Admin API 查询该折扣是否仍存在。实现前不得假定 GraphQL 查询名称或返回字段。
2. 对账触发点包括：打开活动列表或详情、商家准备编辑/暂停/发布活动、进入应用时的限频后台检查，以及每日后台对账。
3. 若平台明确返回“折扣不存在”，立即停止该活动的前台组件数据，随后将本地活动改为 `paused`，暂停原因写为 `platform_discount_deleted`，发布记录清除 `discountId` 并回到可重新发布的状态。
4. 后台列表和活动详情必须显示“SHOPLINE 中的折扣已被删除”的明确状态，不能继续显示 Active，也不能把它误写成订阅失效。
5. 若平台查询超时、网络失败或返回不确定结果，本地发布记录改为既有 `needs_reconciliation`，前台 fail closed，不显示优惠；不能在未确认折扣不存在时清除 ID 或标记 Paused。
6. 商家确认规则仍正确后，使用正常发布流程重新创建平台折扣；不允许静默自动重建，避免意外恢复促销。

该对账流程与订阅失效流程独立：一个店铺订阅有效但平台折扣被人工删除时，只影响对应活动，不影响其他活动，更不会影响其他店铺。

## 失败处理和安全规则

| 场景 | 必须行为 |
| --- | --- |
| 伪造或手动打开支付回跳 | 查询订单和订阅；无确认权益绝不开通。 |
| Webhook 重放/重复 | 幂等记录防止重复试用和重复暂停。 |
| Webhook 乱序 | 新同步版本优先；旧失效事件不能覆盖新有效权益。 |
| Partner API 不可用 | 保留最近确认状态并重试，不猜测性暂停。 |
| 平台优惠暂停失败 | 前台已隐藏组件；后台持续重试至平台确认。 |
| 商家在 SHOPLINE 删除应用折扣 | 对账确认存在缺失后，将该活动标为 `platform_discount_deleted` 暂停；未确认时设为 `needs_reconciliation` 并停止前台展示。 |
| 店铺 A 失效 | 仅处理 `handle=A` 的权益、活动、缓存、锁和任务；店铺 B 保持自己的独立权益。 |
| 绕过页面守卫 | 服务端返回 `SUBSCRIPTION_REQUIRED`。 |
| Token 泄露风险 | Token 不得写入浏览器、日志、错误信息或测试快照。 |
| 试用后重装 | 试用账本保留，只显示付费订阅路径。 |

## 验收标准

### 试用与支付

- 新店铺可通过唯一月付套餐开始一次 7 天试用。
- 创建支付链接后离开，不消耗试用资格。
- 已确认试用恰好为 `(app_key, handle)` 消耗一次资格。
- 重装、更换浏览器或再次结算均不能让同一 `handle` 二次试用。
- 试用结束后能购买月付套餐，但不会再获得试用。

### 续费与权益

- 当前存在有效订阅时，自动续费不暂停活动。
- 到期或续费失败后，在确认的 1 天宽恕期内，活动、后台 API 和主题组件都继续可用。
- 失效 Webhook 到达但查询仍有效时，不创建暂停任务。
- 延迟或乱序的失效事件不能覆盖后续有效同步。
- 应用不以本地到期定时器关闭有效店铺。
- 两次确认无有效权益后才进入失效状态。

### 失效与主题前台

- 失效商家访问每个受保护后台页都进入应用内套餐页。
- 套餐页和支付回跳页可访问，不产生重定向循环。
- 即使绕过前端路由，失效店铺仍不能调用变更 API。
- 全部 Active 活动均进入幂等暂停队列，并通过现有安全暂停流程处理平台优惠。
- 失效店铺的公开活动接口不返回活动数据。
- 主题扩展无权益时不显示，并删除已经挂载的旧组件。
- 续费成功只恢复访问，不自动恢复历史活动。
- 店铺 A 失效不会改变店铺 B 的路由权限、活动状态、前台活动数据或发布任务。

### 平台折扣对账

- SHOPLINE 已确认找不到某个 `platformDiscountId` 时，本地活动不再显示 Active，主题扩展不再展示该活动。
- 仅该缺失折扣对应的活动被暂停；同店铺其他有效活动和其他店铺均不受影响。
- 平台查询不确定时，活动进入 `needs_reconciliation` 并 fail closed，不能错误声称平台折扣已删除。
- 商家必须明确重新发布，应用不自动创建新的平台折扣。

### 验证范围

- 单元测试：权益判定、试用账本唯一性、事件乱序、自动续费保护、路由例外。
- 集成测试：试用、已付费、`grace`、`pending`、`preorder`、过期、支付失败和查询失败。
- 活动测试：每个 Active 活动仅创建一个暂停任务；重试不影响无关活动。
- 主题扩展测试：无权益/无活动响应后 DOM 中不保留组件。
- 租户隔离测试：店铺 A 失效、收到重复 Webhook 或发布对账失败时，店铺 B 的权益、活动、缓存和前台响应不变。
- 发布对账测试：平台确认折扣删除后活动进入 `platform_discount_deleted` 暂停；不确定查询进入 `needs_reconciliation`；二者均停止前台展示。
- 必须在认证的 SHOPLINE 开发店手工验证支付收银台、真实 Webhook 注册与签名、自动续费时序、平台优惠暂停以及前台主题行为。Mock 测试不能标记这些平台行为为已验证。

## 不在本期范围内

- 多套餐、升降级、增值服务和按量计费。
- 自助取消订阅或退款。
- 没有平台可信商家主体 ID 时的跨独立店铺试用限制。
- 续费后自动重新发布活动。

## 实现前置条件

- 从官方 Webhook 文档确认最终 topic、载荷、签名校验、重试和注册方式。
- 在展示“管理套餐”前确认实际可用的 SHOPLINE 套餐管理入口或 API。
- 确认后台暂停任务可以持久化取得 SHOPLINE Admin 会话/Token；否则需设计重新授权恢复流程。
- 确认主题扩展能在活动接口返回失败或无活动后，移除已经挂载的组件。
