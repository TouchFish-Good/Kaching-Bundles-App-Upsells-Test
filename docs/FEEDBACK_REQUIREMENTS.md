# 需求与建议（Roadmap & Feedback）需求说明

**阶段：** 阶段 1，设计已完成，尚未实现。
**模块标识：** `feedback-board`
**商家可见名称：** 需求与建议
**英文名称：** Roadmap & Feedback

## 1. 目标与边界

已认证的 SHOPLINE 商家可提出产品建议、在公开建议上按店铺投票，并查看开发状态与官方回复。建议内容在应用商家之间公开，但提交者身份只供受保护的管理侧审计，绝不出现在商家 API 或页面中。

一期包含建议、投票、相似建议、五种状态、状态历史、隐藏/恢复、官方回复和受保护的管理 API。它不包含商家评论、附件、富文本、通知邮件、第三方 AI 搜索、公开 Developer Admin Console 页面或数据删除工作流。

## 2. 已验证的项目约束

| 项目事实 | 对设计的影响 |
| --- | --- |
| 商家端为 Vite + React 18 + `react-router-dom`，使用 `useAuthenticatedFetch` 注入嵌入式 SHOPLINE JWT。 | 商家页面复用现有鉴权 fetch、路由和 CSS Modules，不从浏览器传入或信任 `shop_id`。 |
| Worker 为 Hono + Cloudflare D1；已有 `requireShoplineSession`。 | 所有商家 API 均在 Worker 中由服务端解 JWT、读取安装会话并解析 `store_id`。 |
| `shopline_sessions.store_id` 和 `admin_stores.store_id` 已由 OAuth 写入。 | 反馈表使用可信 `store_id`，而非可伪造的 handle 或请求体字段。 |
| 已存在 D1 迁移、Vitest 和内部 HMAC 保护的 `/internal/admin-read/v1`。 | 新表放入顺序迁移；管理 API 复用重放保护模式，但需补足管理员身份来源。 |
| 当前应用采用 Sea/Mint/Coral 紧凑运营台令牌。 | 视觉以 `DESIGN_TOKENS.json` 和现有后台截图为准，不采用通用搜索工具给出的新蓝色/字体方案。 |

## 3. 功能需求

### 3.1 提交建议

- 仅已认证且当前安装有效的店铺可提交。
- `title` 为去首尾空白后的纯文本，必填，1--100 个 Unicode code point；`content` 必填，1--5000 个 code point。
- 默认 `status=pending`、`visibility=public`；提交后立即出现在公开列表。
- 客户端按钮在请求中禁用；服务端接受 `Idempotency-Key`，以店铺范围保证同键重试返回同一建议。
- 提交入口固定为“建议”按钮；点击后弹出仅含标题、内容、取消和提交操作的建议弹窗。成功反馈必须沿用应用现有 App Bridge 成功消息，不使用页面内自定义成功 toast。
- 同店铺在 10 分钟内再次提交完全相同的规范化标题与内容，返回可恢复的 `409 DUPLICATE_SUBMISSION` 及已创建建议摘要；不能以相似词直接拒绝提交。
- 内容是纯文本。服务端规范化 Unicode、移除 NUL/不可显示控制符、限制长度；所有前端和管理端渲染必须使用 React 文本节点，禁止 `dangerouslySetInnerHTML`。日志不得记录完整内容。

### 3.2 公开列表与详情

- 所有已认证店铺可看见 `visibility=public` 的建议；返回标题、摘要、发布时间、票数、状态、当前店铺是否已投票、公开官方回复存在性。
- 支持 `sort=newest|votes`、状态筛选、标题和内容搜索、游标分页和详情查看。
- 列表与详情绝不返回提交店铺名、店铺 ID、邮箱、员工或令牌。作者统一显示“商家提交”。
- 隐藏建议必须同时从列表、搜索、相似建议和公开详情消失；访问其公开 ID 返回不可区分于不存在的 `404`。

### 3.3 投票

- 每个 `store_id` 对每个建议最多一票；同店铺员工共享此票。
- `PUT` 幂等地确保已投票，`DELETE` 幂等地确保未投票；二者都返回当前 `voteCount` 和 `votedByCurrentStore`。
- 数据库复合唯一约束是最终一致性边界。票数由数据库触发器更新，不能由浏览器传入或盲目加减。
- 所有未隐藏建议均可投票，不因状态变更而关闭。

### 3.4 状态、可见性和回复

- 固定状态：`pending`（待定）、`approved`（已批准）、`in_progress`（开发中）、`released`（已上线）、`rejected`（被拒绝）。商家只读。
- 每次状态变化写入不可由商家修改的历史：原状态、新状态、操作者、时间和可选备注。商家时间线不展示管理员身份。
- 隐藏独立于状态；管理员必须提供 1--500 字符的隐藏原因，恢复公开时保留历史。
- 官方回复为一对多纯文本记录，含创建/修改时间及独立可见性；商家只能看公开回复，不能创建、编辑或伪造官方身份。

## 4. 非功能需求与验收映射

| 要求 | 验收方式 |
| --- | --- |
| 认证、店铺隔离 | 未带 JWT、伪造店铺字段、卸载店铺都被拒绝；投票/提交使用服务端 `store_id`。 |
| 并发一致性 | 并发投票仅产生一行和一次票数变化；并发取消不会将票数变负。 |
| 防滥用 | 提交、投票和搜索采用按 `store_id + 路由` 的独立限流；写操作有大小限制和幂等键。 |
| XSS/注入 | 带 HTML/脚本的输入只作为文本显示；SQL 全部使用参数绑定。 |
| 性能 | 公开列表和搜索分页；为可见性、状态、时间、票数、投票关系设置索引；首期不引入 AI 服务。 |
| 可访问性 | 可键盘完成搜索、筛选、投票和提交；错误摘要可获焦；状态不用颜色单独表达。 |

## 5. 待确认与风险

1. 当前内部管理认证是共享 `ADMIN_INTERNAL_SECRET` HMAC，并不能证明某个开发者是谁或有什么角色。没有可信的 Developer Console JWT/SSO issuer 前，不能如实声称已满足“独立管理员身份认证与 RBAC”。
2. 是否让 Roadmap & Feedback 受 Ultra 订阅权限限制尚未确定。推荐默认向所有已安装且认证的应用商家开放，避免将产品反馈渠道绑定到付费 entitlement；需要产品确认。
3. 商家可见回复的修改历史、隐藏理由是否展示给商家尚未要求。推荐一期仅展示当前公开回复、公开状态时间线和状态备注，不展示管理员身份、内部审计或隐藏理由。
4. 当前 D1 schema 没有全文检索表。首期使用参数绑定的大小写无关 `LIKE` 及最小查询长度；数据量增长后再用经验证的 D1 FTS 能力迁移，不能假定扩展可用。
